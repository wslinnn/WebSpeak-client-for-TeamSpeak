# WebSpeak 0.3.1

修复 0.3.0 之后发现的三个语音播放问题。三项都出在浏览器侧的播放链路，网关与服务端协议没有改动，升级后刷新页面即可生效。

## 修复

### 移动端听别人说话发闷

协商 WebRTC 音频时，网关会把浏览器 offer 里的 Opus 参数原样回声进 answer。此前只覆盖了码率上限与 DTX，没有处理 `maxplaybackrate` —— 那是接收端自报的播放带宽上限。部分移动浏览器为省电并对齐系统语音处理路由，会声明 `16000` 或 `24000`，回声后解码带宽被限制在 8 kHz / 12 kHz，听感就是明显的「闷、糊、像低码率」；桌面端通常声明 `48000` 或不发该参数，所以同一路语音在桌面正常。

现在两个方向都钉到 `48000`。下行 payload 本身就是全频带 Opus 字节透传，这个值才如实反映内容，且不增加带宽占用。

### 调节音量后播放持续变调、变速

为兼顾「超过 100% 的增益」与「选择非默认输出设备」，0.3.0 把增益管线接进了一路共享混音总线，再由第二个隐藏元素播放。这条链路把音频送过三个互不重采样的时钟域——WebRTC 接收器、AudioContext、媒体元素——时钟漂移持续累积，只要管线还在就不会自愈，因此调节中和调节后都不正常。

现在增益管线直连音频设备，只有单一时钟域。代价是放大的增益无法跟随非默认输出设备，因此选择其它输出设备时会把超过 100% 的增益钳到 100%，走可路由的元素路径；默认输出下放大照常工作。

### 衰减音量被迫走增益管线

同一处改动的连带修复：此前任何非 100% 的音量都走增益管线，包括本该由元素音量完成的衰减。现在按平台能力分流——运行时探测元素音量是否真正生效（iOS Safari 会忽略写入），生效时衰减留在元素路径，不再付出管线开销。

## 升级说明

- **Docker**：`docker compose pull && docker compose up -d`。
- **发布包**：下载对应平台的包替换程序文件，保留 `data/` 目录与 `master.key`。
- **源码**：`git pull` 后重新安装依赖并构建前后端。

数据库 schema 未改动，无需迁移。

## 验证

GitHub Actions 通过自动化测试、类型检查、前后端构建、Playwright 冒烟与 Docker 启动健康检查；Windows 与 Linux 发布包在独立目录执行内置健康检查。

需要说明的是：上述三个音频问题的修复依据是代码与协议层面的分析，**未在真实移动设备上逐项复测**。自动化构建通过不代表已完成真实语音环境下的听感验收。
