### WebRTC 下行编码连续性修复（2026-10-03）

- 将前次实服音量异常缩小到实际 `WebRtcAudioSession` 混音器，用手动推进音频时钟排除网络和调度影响；源编码、网关解码和输出解码均使用原生 Opus。旧路径中，50 个语音帧与静音交替时，50 个输出全部低于 RMS 100；同样输入强制重编码后 50 个全部超过门槛。这证明存在独立于网络的代码故障。
- 原因是单人且音量为 1 时直接转发源 Opus，静音、音量变化或多人混音则使用网关编码器；同一 RTP 流交替携带不同编码器历史，接收端无法维持连续解码状态。现在全部下行音频通过同一个会话编码器，删除原始 Opus 直通分支；队列、节拍、成员音量和上行路径保持原规则。
- 新增 3 项回归覆盖静音间隔、交替说话者和音量变化，每项 50 个活动输出均达到预期电平，解码错误及队列丢弃为 0。本批一次统一验证通过 419 项测试及前后端构建。代价是单人默认音量也需要重编码，增加编码工作和一次有损转换；尚未完成容量压测。
- 实服复查使用 `<TS3_TEST_HOST>:9987`、两个临时身份与本机 werift 端点。下行 50 个发送帧中网关收到 46 帧、向混音器提交 46 帧，队列丢弃和上下行解码错误均为 0；解码输出有测试音频。RMS 超门槛输出计数为 70，包含编码尾音，不能解释为 70/50 帧交付或完整音质通过。

### 音频分段复查与协商失败回退（2026-10-03）

- 针对前次伴奏 27/30 的帧差，临时测试进程记录 UDP 发送回调、接收数据报、解密后的音频包序号、SDK 事件和 WebSocket 输出，不修改生产诊断或 SDK。三轮静音伴奏各发送 50 帧，各段计数均为 50，序号分别为 0–49、50–99、100–149，无发送错误或网关输出丢弃；每次停止伴奏后再发送 10 帧均被静音抑制。此次未复现原帧差，不能倒推原故障原因或声称永不丢帧；不继续无差别重复探测。

### 06-H 身份文件读取的异步归属

原入口为 `28eda60` 中的 `WebClient.vue` 文件读取、弹窗开关与卸载函数。当前实现见 [useWebClientIdentity.ts](../web/src/composables/useWebClientIdentity.ts) 与 [IdentityImportDialog.vue](../web/src/components/web-client/IdentityImportDialog.vue)。

### 04-J 诊断采样与展示只比较同一来源

当前实现：[audio-diagnostics.ts](../web/src/voice/audio-diagnostics.ts) 与 [useWebClientPerformance.ts](../web/src/composables/useWebClientPerformance.ts)。原面板直接相减前后样本中的下行计数，来源可能分别为 RTP 包、兼容音频帧或网关发送帧。peer 替换后新计数若大于旧值，也会被误当成同一流的增长。采样失败时保留旧活动状态，已排队的旧轮询会设置运行标志却无法清除；卸载后手动刷新仍能发起请求。

已实施：采样模块拥有等待登记、总期限、兼容计数和浏览器统计。样本携带仅用于浏览器内部的 `scopeId`，不修改网关协议；连接或传输变化以及会话释放会使范围失效。兼容计数随会话重置，旧快照保持独立。面板只比较相同范围、传输和下行计数来源；缺失或拒绝的采样清除旧状态，下一样本重新建立基线。轮询开始前与结果返回后均校验代次，卸载同时禁止旧回调和手动刷新。

[W3C WebRTC 统计定义](https://www.w3.org/TR/webrtc-stats/#dom-rtcsentrtpstreamstats-packetssent) 将 `packetsSent` 定义为已发送包总数。据此，上行丢包估算分母使用发送数，不再重复加上丢失数；下行仍以接收数加丢失数计算。浏览器提供的 `fractionLost` 用于采样中的上行百分比，否则按计数估算。RTCP 反馈和本地计数采样时间可能不同，不能将该估算表述为精确网络测量。

已验证：10 项实际 Vue 状态用例，其中 8 项先失败后通过；语音会话新增 3 项范围与重连用例并增强 1 项丢包率断言，均先失败后通过。保留每 2 秒轮询、采样总期限和已有音频状态提示。并行运行时发现 Vite 即使关闭 HMR 仍监听默认 WebSocket 端口，三个无界面测试入口现同时设置 `ws: false`，无需占用该端口。

## 近期修复的浏览器媒体问题

### 04-E 保留可用发送链并完整清理失败候选

修改前位置：`c9740c4` 中 [useVoiceWebSocket.ts](../web/src/composables/useVoiceWebSocket.ts) 的混音创建、替换和伴奏启停函数，原第 752–918 行。当前实现位于 [webrtc-input.ts](../web/src/voice/webrtc-input.ts) 和 [accompaniment.ts](../web/src/voice/accompaniment.ts)。

原实现的顺序及缺口：

- `createWebRtcMixStream` 先调用 `stopWebRtcMix`，其中会停止当前输出音轨；之后才创建新节点并调用 `sender.replaceTrack`。创建或替换失败时，旧音轨已经结束，没有可用旧链供回滚。
- 更换伴奏时，在混音接入成功前就停止旧伴奏，并发送 `active: true`。失败后再发送 `false`，无法保留原本正常的伴奏；错误统一归为 `permission`，也不能区分用户授权与音频处理失败。
- 混音节点先在局部变量中创建，之后才写入清理函数使用的引用；如果中途创建或连接失败，已取得的候选节点及输出音轨缺少完整释放路径。
- 停止伴奏也会重建整个混音并替换发送轨道，因而停止操作同样依赖新节点分配成功。

本批通过故障注入实际复现旧发送轨道结束、旧伴奏丢失、部分节点及输出音轨未释放、停止依赖新分配，以及混音节点释放异常中断会话清理。测试使用实际 composable 和浏览器边界替身，不代表已测真实浏览器的故障频率或音质。

已实施：每个 WebRTC peer 保持稳定输出轨道，仅接入或移除伴奏源；新源连接成功后再解除旧源并停止旧采集。混音模块拥有节点和输出流，独立释放部分分配及关闭资源。只有接入成功后才更新活动状态；音频处理失败使用独立错误码和五语提示，可选内容提示失败不再遗留采集。

已验证：节点分配或连接失败保留原麦克风输出与旧伴奏；启停伴奏不结束或替换发送轨道；停止不依赖新输出分配；候选失败和重复清理释放所属资源。麦克风静音和音量设置在启停期间保持有效，伴奏不经过麦克风降噪与增益，也不额外添加固定衰减。

### 04-F 停止操作立即释放已取得的候选采集

位置：[accompaniment.ts](../web/src/voice/accompaniment.ts)，由语音入口调用；回归位于 [voice-session.test.mjs](../web/test/voice-session.test.mjs)。以下描述修改前的行为。

`getDisplayMedia` 返回后，候选 `nextStream` 在等待 `applyConstraints` 期间仍是局部变量。停止或断开只清理已提交的 `accompanimentStream` 并使代次失效；候选流需等约束 Promise 结束，执行后续失效检查才被停止。现有取消用例也是先结束约束等待，再断言音轨已停止，没有覆盖立即释放。

此外，音轨的 `ended` 监听在约束等待后才注册，提交前也没有检查 `readyState`。若用户在等待期间结束采集，代码仍可能将已结束的音轨标记为活动。

已实施：伴奏控制器同时拥有当前流和已取得但未提交的候选流。停止、断开或新操作取代旧操作时，立即释放候选资源；仍未返回的授权请求在结果到达时立即释放。操作绑定原混音目标与代次，提交前复核目标和音轨状态，旧结束事件不能停止新采集。

已验证：约束 Promise 未完成时音轨已经停止；等待期间结束采集不会发送活动状态；迟到授权和旧失败不影响新伴奏。现有四项伴奏用例继续保留，其中取消用例增加立即释放断言；另验证无音频来源失败保留旧伴奏、断开清除旧错误，以及采集处理约束与五语错误映射。

### 04-G 电平监测失败不影响语音与后续连接

位置：[microphone-meter.ts](../web/src/voice/microphone-meter.ts)，由语音入口的监测启停函数组装。

原实现只在全部节点连接完成后才记录清理引用，分析器分配或连接失败会遗留先前创建的节点。计时器回调读取全局分析器引用，已排队的旧回调会读取替代连接的分析器并更新电平；读取异常没有受控处理，释放异常也可能中断 peer 和麦克风清理。五项故障用例均在修复前复现。

已实施：每个监测实例独立拥有节点与计时器，停止先使回调失效，再逐项释放资源。准备或读取失败只停止电平监测，清除电平与发言提示，保留麦克风流和语音 peer。已验证 512 点采样、50 ms 周期、原有 RMS 电平比例及上限保持一致；此处不声称真实设备的电平与音质已验收。
